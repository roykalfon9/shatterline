# SHATTERLINE

A portrait arcade brick breaker with five authored arenas, three lives, paddle-edge
aiming, and three falling power-ups. Built with Unity **6000.3.20f1**, URP 2D,
TextMeshPro and the Input System.

## Run

Open the project in the matching Unity editor, open `Assets/Scenes/Game.unity`,
and press Play. The saved scene is ready; scene-generation commands are not
required. They are authoring tools and can overwrite scene customization.

- Move: A/D, arrow keys, mouse, or gamepad stick/D-pad. On a phone, drag relatively.
- Launch: Space, click, gamepad south button, or a short phone tap.
- Pause: Escape, gamepad Start, or the bottom-left pause button.
- Menus: mouse/touch, or directional navigation and Enter/Space/gamepad south.
- Catch capsules for an eight-second wider paddle, eight-second slow ball, or up
  to three simultaneous balls. Only losing the final active ball costs a life.
- Clear all bricks to advance. After the fifth arena, layouts repeat and the
  displayed level number continues increasing. Two-hit bricks crack on the first hit.

## Validation and builds

Run **Tools > Shatterline > Run Playability Tests**. The real-scene Play Mode suite
writes `Logs/PlayabilityTests.xml`. See [validation evidence](Docs/Validation.md)
for the latest result and the limits of simulated input testing.

Player build commands are under **Tools > Shatterline**:

| Command | Output | Required module |
|---|---|---|
| Build Windows Player | `Builds/Windows/Shatterline.exe` | Windows build support compatible with the selected backend |
| Build Android Player | `Builds/Android/Shatterline.apk` | Android build support, SDK/NDK tools and OpenJDK |

The revised Windows build succeeds and is packaged at
`Builds/Submission/Shatterline-Windows.zip`. Extract the whole archive before
running; all data/runtime files are required. Windows hardware testing remains
outstanding. Android build verification is in progress.

A supplemental local Mac build is available at `Builds/Mac/Shatterline.app`
(**Build Mac Test Player** in the same menu). Startup, launch, scoring, pause,
keyboard resume and return-to-menu were exercised in this actual player.
This does not certify Windows/Android behavior. Build receipts are written under
`Logs/Build-<target>.json`; the helper rejects reports with errors or missing output.

## Code and patterns

| Concern | Implementation | Why it exists |
|---|---|---|
| Object Pool | `ObjectPool<T>`, used by `GameManager`, `PowerUpSpawner`, `BrickGrid` | Bounds balls/capsules/particles; refuses extra balls when full and recycles old visual effects |
| Singleton | `GameManager.Instance`, `AudioManager.Instance` | One run owner and one audio owner per scene; duplicate instances are rejected |
| Finite state machine | `GameState`, `GameManager.SetState` | Central transitions, UI selection and one transition coroutine at a time |
| Data assets | `GameConfig`, `LevelData` | Inspector tuning and five level layouts without changing gameplay code |

The enum state machine is not the polymorphic GoF State pattern. Coroutines are
Unity sequencing tools, and ScriptableObjects are data assets; describe them
accurately if the course requires specific named design patterns. Singleton access
also creates global dependencies, so it is confined to the two owners.

Physics and aim live in `BallController`; pointer/rate-based paddle movement in
`PaddleController`; score and run lifetime in `GameManager`; display in `UIManager`.
Editor-only authoring/build/test helpers live under `Assets/Editor`, and test code
has a separate assembly. Important pool, input-consumption and timer invariants
have comments at the relevant code.
